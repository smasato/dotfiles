# OMP で pstack を使う

この dotfiles で配置した pstack を、OMP から呼び出す手順です。上流の完全なコピーではなく、既存の作業フローに合わせたローカル移植版を使います。導入と更新の仕組みは [pstack の構成・保守](README.md) を参照してください。

## 最初の依頼を送る

1. 対象リポジトリをカレントディレクトリにして、ターミナルでスキルの読み込みを確認します。

   ```sh
   omp read skill://poteto-mode
   ```

   `~/.agents/skills/poteto-mode/SKILL.md` の内容が表示されれば、スキルを認識しています。このコマンドは読み込むだけで、作業を実行しません。

2. OMP を起動します。

   ```sh
   omp
   ```

3. OMP の入力欄に、スキル名と依頼を入力します。

   ```text
   /skill:poteto-mode このリポジトリの設定読み込み処理を調査し、改善案をまとめて。今回は読み取り専用。提案を出したら止めて。
   ```

   調査結果、根拠、改善案を確認します。実装も依頼する場合は、対象と検証方法を続けて伝えます。

OMP での呼び出しは `/skill:<名前>` です。以下のスキルは明示起動用なので、必要な作業で呼び出してください。`pstack-runtime` は実行ルールの参照先であり、通常は直接呼び出す必要がありません。

## 作業に合うスキルを選ぶ

以下は OMP の入力欄へ送る例です。対象と完了条件をプロジェクトに合わせて置き換えてください。

### 通常の調査・実装には poteto-mode を使う

```text
/skill:poteto-mode 保存ボタンを連打すると同じデータが重複登録される。再現して原因を修正し、実動作で確認して。コミット・PR作成は不要。
```

調査、実装、検証を依頼範囲内で進めます。ローカル版は、毎回の設計コンペ、コメント監査、PR 作成を要求しません。結果では、修正内容だけでなく、実行した確認と未確認事項を見てください。

### 独立した作業を分担するには swarm を使う

```text
/skill:swarm 認証処理とキャッシュ処理を2人で分担して調査して。読み取り専用。責務、依存関係、問題点を最後に1つの報告へまとめて。
```

親が作業を分け、結果を統合します。実装を分担させる場合は、書き込み先や共有状態の所有者も決めます。同じファイルや同じ Git 操作を複数の担当者に同時変更させないでください。

### 異モデルで差分をレビューするには interrogate を使う

```text
/skill:interrogate 未コミットの変更をレビューして。目的は設定読み込み時の重複処理をなくすこと。異なるモデルで独立に確認し、根拠付きの指摘を統合して。修正はしないで。
```

親が同じ意図・差分・評価基準を2つの専用エージェントに渡し、指摘を統合します。レビュー対象を明確にするため、未コミット変更、比較元のブランチ、対象ファイルのいずれかを指定してください。

専用エージェントは読み取り専用です。シェル、編集、追加委譲のツールを持たないため、実行時の証拠は親が用意します。修正やテスト実行が必要になったら、レビュー結果を確認して別途依頼してください。

### 複数案を比較するには arena を使う

```text
/skill:arena 設定保存方式を2案で比較して。評価基準は障害時の復旧、変更範囲、保守のしやすさ。必要な試作は一時領域で行い、本体への反映はせず、採用案と理由を示して止めて。
```

候補を独立に作り、完成後に別の判定役と親が比較します。採用案へ取り込む点と捨てる点を確認してください。判断を比較するときは異なるモデル系列を優先しますが、生成作業では同じモデルの複数試行も使います。

`interrogate` の専用エージェントは、書き込みが必要な候補作成には使いません。利用可能な実装エージェントで必要なモデル構成を組めない場合は、その制約を報告させます。

## レビューのモデルを変更する

まず、対象プロファイルの現在の割り当てを確認します。

```sh
omp config get modelRoles
```

この dotfiles の初期値では、レビュー用の2席を次のように分けています。

| エージェント              | ロール             | 初期モデル                       |
| ------------------------- | ------------------ | -------------------------------- |
| `pstack-review-openai`    | `review_openai`    | `openai-codex/gpt-6-astra:high`  |
| `pstack-review-anthropic` | `review_anthropic` | `anthropic/claude-opus-5-5:high` |

1. OMP で `/model` を開き、**Roles** から変更するロールを選びます。
2. そのプロファイルで利用できるモデルを割り当てます。異モデルレビューを続ける場合は、2席を別のモデル系列にします。
3. `/agents` で専用エージェントのモデル指定も確認します。エージェント別の上書き設定がある場合は、ロール参照よりそちらが優先されます。

通常の `reviewer` は `review` ロールを使い、この2席とは独立しています。親の会話モデルを変更しても、レビュー用ロールは変わりません。`plan` ロールの設定や todo の作成だけで、親が自動的に計画用モデルへ切り替わるわけでもありません。

モデル選択は OMP の設定で管理します。別の pstack 用モデル設定ファイルは作りません。chezmoi の設定テンプレートは既存のモデル割り当てを保持するため、上表と現在値が異なる場合は現在値を確認してください。

設定の管理元は [通常プロファイルのテンプレート](../../dot_omp/private_agent/modify_private_config.yml)、エージェント定義は [OpenAI 側](../../dot_omp/private_agent/agents/pstack-review-openai.md) と [Anthropic 側](../../dot_omp/private_agent/agents/pstack-review-anthropic.md) です。

## 進行状況と結果を確認する

- 実行中の担当者は **Alt+A** の Agent Hub で確認します。モデル、状態、活動内容を見て、必要なら対象の履歴を開きます。
- モデル割り当てを確認・変更する場合は `/agents` を使います。実行状況の確認と設定変更を区別してください。
- `swarm` では `PASS`、`ISSUES`、`BLOCKED` と、未完了の担当範囲を確認します。
- `interrogate` では `Act On`、`Consider`、`Noted`、`Dismissed` と、モデル間の一致・不一致を確認します。指摘数の多さだけで採否を決めないでください。

レビュー後は、設定上のモデルだけでなく、実際に動いたモデルを確認します。フォールバックで同じモデル系列になった場合や、片方が実行できなかった場合は、異系列の2モデルレビューが完了したとは扱いません。エージェント名が2つあることだけでは独立性の証拠になりません。

## 権限・プロファイル・利用量を決める

### 依頼の停止点を明示する

調査、編集、コミット、PR 作成、マージのどこまで任せるかを依頼に含めます。スキルを起動しただけで、すべての操作を許可したことにはなりません。レビューだけなら「読み取り専用」、実装までなら「コミット・PR 作成は不要」のように境界を伝えてください。

長時間の作業を中断するときは、完了した作業、未完了の作業、検証結果、次に許可する操作をまとめさせます。バックグラウンドの CLI watcher は、OMP 終了後のモデル実行を保証しません。再開時には、引き継ぎメモと実際のファイル・プロセス状態を照合させます。

### 別プロファイルでは認証も確認する

experimental を使う場合は `omp --profile experimental`、security を使う場合は `omp --profile security` で起動します。

両プロファイルは共有スキルと専用レビューエージェントを使いますが、設定、認証、セッションは別です。対象プロファイルで `/login` を使い、利用するプロバイダーへログインしてください。通常プロファイルでモデルが動いたことだけでは、別プロファイルでも動くとは限りません。

プロファイルはサンドボックスではありません。プロジェクト設定や環境変数から渡された認証情報も適用されます。用途やアカウントを分ける場合は、対象リポジトリと認証元を確認してください。

### 並列数と利用量を確認する

並列数の上限は次のコマンドで確認します。

```sh
omp config get task.maxConcurrency
```

`swarm` の担当数や `arena` の候補数は、依頼内容に応じて指定します。上限は常に起動する人数ではありません。候補数やレビュー人数を増やす前に、利用量と認証先の制限を確認してください。

## 更新・不具合を切り分ける

### スキルが見つからない

ターミナルで、配置と有効化設定を確認します。

```sh
omp read skill://interrogate
omp config get skills.enabled
omp config get skills.enableAgentsUser
omp config get skills.enableSkillCommands
```

読み込みが失敗する場合は、共有ストアへの配置と対象プロファイルを確認します。ファイルがない場合は、[導入手順](README.md#導入と更新) に従って chezmoi から配置してください。配置や設定を直した後は、OMP を再起動して入力候補を確認します。

この構成では、`omp plugin list` が `No plugins installed` と表示しても異常ではありません。スキルは chezmoi から配置しているため、復旧のために upstream プラグインを重ねてインストールする必要はありません。

### レビュー担当やモデルが使えない

`/agents` に `pstack-review-openai` と `pstack-review-anthropic` があるか確認します。見つからなければ、chezmoi でエージェント定義を配置した後に OMP を再起動してください。

モデルが想定と異なる場合は、ロールとエージェント別上書きを確認します。

```sh
omp config get modelRoles
omp config get task.agentModelOverrides
```

別プロファイルを調べる場合は、コマンドにもプロファイルを指定します。

```sh
omp --profile experimental config get modelRoles
omp --profile security read skill://interrogate
```

認証やモデルの利用権限が不足している場合は、対象プロファイルの `/login` と `/model` で確認します。片方しか動かない状態では、結果に不足を明記させてください。

### スキルを保守する

スキルは `dot_agents/skills/`、OMP の設定とエージェント定義は `dot_omp/` のソースを編集します。配置済みファイルを直接編集せず、差分を確認して chezmoi で適用してください。モデル選択は前述の OMP の設定画面で変更できます。

上流更新は自動追従せず、必要な差分だけ取り込みます。[upstream 記録](../../dot_agents/skills/pstack-runtime/references/upstream.json) の `selectiveUpdates` で、採用元コミットと変更内容を確認できます。記録されたバージョンの全機能を取り込んだという意味ではありません。

スキルを変更した後は、[pstack の検証手順](README.md#検証) を実行します。PR 監視やスタック操作も使う場合は、Bun の依存パッケージ、GitHub 認証、gh-stack を確認してください。これらは通常の読み取り専用調査を始めるための追加条件ではありません。

エージェント側の具体的な実行ルールは [OMP アダプター](../../dot_agents/skills/pstack-runtime/references/omp.md) を参照してください。
